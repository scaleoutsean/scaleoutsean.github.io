    Object stores solved the problem of data sharing in hybrid cloud years ago

    2026-08-02 00:00 5 minute read

    On this page

    • Introduction
    • Azure OneLake with NetApp StorageGRID
    • Conclusion

    Introduction

    For over a decade now, I've been hearing about "challenges" of data sharing in hybrid cloud environments. Yes, it used to be difficult, but that's no longer the case. Why are we still hearing about that?

    That problem has been mostly solved.

    In the 2010s, file sharing was a problem that needed solving. Usually there would be human users working on SMB or NFS shares. Challenges were overcoming challenges (or replacing with own client) chatty SMB and NFS protocols, implementing fast global locking, and so on.

    Today, we have data sharing in workflows. Usually, it's data stored in objects and sometimes queried from databases backed by object storage.

    Most users are machines and they use S3. Access works over HTTPS with post-quantum encryption, real-time event notifications, auditing, read caching, and everything can be easily integrated in data lakehouse patterns and workflows. It generally works very well.

    Even for "traditional" applications, S3 access works fine. There's AWS Mountpoint S3, there's ObjectiveFS and there are other ways that enable data sharing in hybrid cloud environments.

    For databases, it is even easier. For over half a decade now, databases have been using external tables located on S3. I blogged about SQL Server PolyBase years ago. On the front-end, it's SQL Server, on the back end, it's Parquet. We can run SQL Server anywhere and still get to our data, as long as SQL Server can reach S3.

    In 2022, I blogged about PostgREST which allows RESTful access to on-premises databases using HTTPS, freeing us from the need to use VPNs or replicate data for Tier 3 and Tier 2 applications in the cloud. I ran my front-end application in CloudFlare and my back-end was PostgreSQL located on-premises, attached to SolidFire. It worked perfectly fine.

    There are many ways to do this more reliably for use cases that need that, by caching a replicated subset, directing writes to on-premises, and more. These are all solved problems.

    These days, we have datalakes in which databases fully live in object stores. Both databases and file/object content is in the same place. It works from anywhere and it's even better than with file sharing because you cover structured, semi-structured and unstructured with one storage solution that can be deployed anywhere and accessed from anywhere. Caching can be done on massive scale from various query engines and clients.

    Snowflake external tables that make it easy to use StorageGRID data have been available since 2022 as well.

    I actually like this misspelling very much, which is why I highlighted it so that you don't miss it. The screenshot is from a Snowflake-StorageGRID solution brief and perhaps a good proxy for how many people actually paid attention since the document was published years ago.

    DeltaSharing has made sharing on your own terms very easy, because entire open source-based stacks could be built for shared access to object stores without even having to manage S3 credentials to every user. Now we have OpenSharing and there are free reference servers anyone can use. There's no need for S3 credentials for every user, no need to reinvent the wheel for any of the S3-related features I mentioned above (event notifications, audit logs, encryption, read caching, and more).

    Aside from the obvious (what's been possible in Snowflake and SQL Server), you can, for example, run OpenSharing and Versity S3 Gateway on Windows, sharing tables and files to your cloud-based applications running anywhere. You don't even need to use Linux!

    I'm not encouraging anyone to use my implementation or even use OneLake shortcuts or OpenSharing. I'm just showing that these things work today, even in freeware implementations.

    So what exactly is the problem? What kind of sharing in hybrid cloud is hard? I don't get it. I haven't seen one so far in this decade.

    I only see improved S3-based solutions appear every month, making existing S3-based solutions better for a vertical or use case.

    Azure OneLake with NetApp StorageGRID

    Azure OneLake has what appears like DeltaSharing that's in the process of implementing OpenSharing to expand its reach to other clouds and on-premises.

    First, you need something called ODG (On-premises Data Gateway).

    Credit (images): Microsoft

    In OneLake, create a shortcut.

    Pick AWS S3-compatible storage.

    Enter shortcut properties, including endpoint of reverse proxy or StorageGRID load balancer.

    We have to use S3 keys because of this limitation, which will likely go away in a quarter or two.

    Currently only key or secret authentication is supported for S3-compatible sources. Microsoft Entra-based OAuth, Service Principal, and RoleArn are not supported.

    This is the same "limitation" my OpenSharing Server for StorageGRID and Versity S3 with E-Series has. There are many moving parts that aren't easy to deal with even in this case where OneLake plans to support only Entra-based OAuth (at least initially), let alone implementing a bunch of supported OAuth services (for Entra and other OAuth that StorageGRID 12.1 supports).

    But, in Azure, almost everyone uses Entra and StorageGRID supports it as well. If you connect to OneLake with OAuth and OneLake authenticates with StorageGRID using Entra, you have end-to-end authentication and authorization.

    OneLake shortcuts support even Iceberg tables. I blogged about Iceberg table support in the OpenSharing Server post here.

    For small (edge) sites, current approach (no Entra and Assume Role) works today even on Windows. Example: OpenSharing for Windows and Versity S3 Gateway for Windows.

    Conclusion

    OneLake shortcuts for on-premises S3 are in preview, but it's only matter of months before it graduates to GA.

    Since OpenSharing was announced, I knew its implementations would take data sharing in hybrid cloud environments to the next level, which is why I've spent time on it myself. It's an evolutionary change that builds upon S3.

    A solution for an already solved problem becomes even better:

    • Structured way to share different content types, from tables to regular files and AI models
    • OAuth avoids micromanagement of S3 credentials, centralizes access, security, auditing and more

    There's no hybrid cloud data sharing problem that any other approach solves better than S3. There's nothing that comes even close - no one bothers with Azure's and GCP's object APIs, and Swift has been deprecated in StorageGRID because no one was using it.

    What you need for data sharing in hybrid cloud is the same thing you needed in 2020: an on-premises S3-compatible object store.
