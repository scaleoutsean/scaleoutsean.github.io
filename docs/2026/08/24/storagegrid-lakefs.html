    lakeFS for data lake AI/ML management and compliance

    2026-08-24 00:00 5 minute read

    On this page

    • Introduction
    • Improve management with lakeFS
    • Conclusion

    Introduction

    Last week, Datalake-ish RAG with (only) NetApp StorageGRID S3 showed how we can perform RAG and run chat without persistent file and block services.

    While that was a basic demo that was focused on storage-related aspects of that stack, this post is meant to show how you can use lakeFS to bring order into those stacks even if you do not use data lake to manage them. The solution (this is a nice video presentation) isn't new, but not many people know about it.

    In some cases - especially when it comes to existing data lake users - we'd integrate such workflows and data management with data lake, as mentioned in that post at the top. In other cases, you may want to use lakeFS in addition to data lake. This used to be "instead", but lakeFS Enterprise lets you do "in addition to" as well as "instead of" (in the case you don't need the complexity of data lake, but still want to use Iceberg tables, for example).

    Improve management with lakeFS

    lakeFS lets us manage buckets in a git-like manner. We can create branches, merge them, undo merges, tag commits and integrate all this with Iceberg data lakes.

    Continuing from that previous post on RAG, one of the things that was mentioned in my simplified demo was data cleansing in Step Two, represented by a simple filtering by content tag. Of course, that's very simple, and in reality we'd have more sophisticated and complicated checks.

    Similarly, my chat bot had no guardrails, but maybe you'd want to add some to it, too (although that's purely a configuration step that is less related to data management). But you may also want to perform chat logging, for auditing and compliance purposes - we could simply stream that to an event sink that would store data to data lake tables.

    To set lakeFS up, we need a PostgreSQL database. If you have several users, just use whatever. If it's important or you have many users, check out CNPG.

    To hook lakeFS with StorageGRID, we also need a bucket. It doesn't have to be called anything in particular - for example my StorageGRID bucket is called s3://lakefs but in lakeFS my project is called scaleoutsean. Once you start, you see a Github-like interface.

    On the back, your bucket will have a data path to something like this:

    Let's see how we could use lakeFS to help with the most relevant requirement, data preparation.

    In Step Two, we'd create a branch to remove PII. We don't want to work on live data or copy stuff around. We create a branch. After processing, we may have an updated content without PII (or with PII masked/redacted).

    Notice that it says "Uncommitted" for the commit.

    We run QA checks and when it's all ready, we may commit.

    Then we'd want to merge this into main to replace or add the currently active file in s3://blog-silver/ from which RAG users get information.

    Notice that authorized users can download using presigned URLs. In fact, lakectl lets you do the whole thing from console, which gives you fastest access to lakeFS and allows you to create seamless workflows. (The Web page at the bottom is README.md being automatically shown).

    If you want to visually inspect, you can diff as you do with git.

    Everything is fine, so we proceed with a merge. Tags such as pii_job (which I inserted manually in the Web UI) could be added automatically if we executed these workflows from the CLI.

    And now the merged content is in main. It's "live".

    Now, if you or other user wanted to check what happened, when, why, how: that works exactly as you'd expect. (Yeah, I misspelled my lakeFS username.)

    You don't have to dig through logs to find your bucket or filesystem snapshots. You don't have to reconcile bucket snapshot with data cleansing job ID or software version.

    It's all there are your disposal and as a user, you can get this info instantly. There's no need to get access to any other system and all other workflows can integrate with lakeFS.

    The above was the "core" stuff.

    lakeFS can now do more. For example, you can work with Parquet files directly from the UI. Here I query lakefs://scaleoutsean/main/lakes.parquet without leaving the UI:

    In my RAG demo application, I have parquet files. I could explore them directly from the UI.

    Any commits can be audited for author, details, tags.

    I can also tag and version my releases. Each is tied to specific commit, so nothing can happen to data without there being anything unclear about it. If something failed, we can find that. If it didn't, it's can be replicated using the data from the branch in which it was created and applications/models used to generate it (assuming we use those tags, as we should).

    One extremely useful feature is git-like hooks. This is what can make a lot of lakeFS operations automated.

    Instead of managing snapshots, replication, clones, and dealing with storage, you deal with workflows and data is managed in the process.

    Conclusion

    There's nothing in RAG and other AI workflows that the S3-only approach is missing. It works on pure data lake stacks, and it can be assisted by lakeFS (if Iceberg integration is used).

    lakeFS does need a PostgreSQL database, but in theory it could use data tables for everything. By the way, the CNPG version of PostgreSQL I mention can perform continuous backup to S3, so what I said still holds - if you orderly shutdown databases and bootstrap from S3, they could be running off ephemeral disks.

    lakeFS used to be a "git for S3", but with Iceberg tables support, it's a lot more.

    StorageGRID has bucket snapshots, but I don't consider them to be an alternative to lakeFS. They get you in storage management business (which is why I offload that task to the otherwise pathetic COSI), and lakeFS gets you out of it.

    With StorageGRID managed from data lake and lakeFS, you literally eliminate most of storage management while not losing, but gaining, value in compliance, auditing, support and more. All without spending more on storage.
