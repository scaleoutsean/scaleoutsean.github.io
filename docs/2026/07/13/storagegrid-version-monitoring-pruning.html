    Monitor and prune object versions on NetApp StorageGRID S3

    2026-07-13 00:00 2 minute read

    Introduction

    Delete old object versions on NetApp StorageGRID talks about ILM-based deletion of old object versions ("non-current" versions, as they call them).

    It's curious how people use (or even don't use!) this feature, and when certain applications make a lot more versions than expected and don't clean up after themselves, they want a "new feature" that "solves this"!

    Version hog pruner

    I create a service that accepts StorageGRID audit log, identify PUTs of interest and store them in a bucket (it could be one per grid, or one per tenant).

    Every so often, I consolidate those into larger data lake tables.

    The above is step (1) below, and that runs on a schedule. Report & Notify in (2) can be scheduled or on-demand.

    In this case the hog is this README.md file that was uploaded many times today.

    Identifying version hogs that bother you is simply a matter of using a custom query and can be modified based on S3 key (bucket name, path, "file name", "extension", version count, total size of all versions, etc).

    Other ways and workarounds

    If you use Elasticsearch integration for search, you can simply query an index and count object versions. If counting object (key) updates doesn't work, ingest audit log instead and use it to produce object "seeing" reports in Kibana or own client (multiple PUT requests on the same S3 key).

    Or, you can use StorageGRID Audit Log Converter (SGAC) script to parse several StorageGRID audit logs and find the worst offenders. In most cases you'd need just 2-3 samples - there's no need to track this 24x7 and have services and overheads if you don't want to mount a sustained effort.

    What about existing non-current object versions

    Let them get processed by the generic ILM rule.

    If you can't wait, run ListBucketV2 on all such buckets, be back in a week to collect results, and use them to create delete jobs for old versions you don't want to keep until ILM cleans them.

    Conclusion

    This is not hard and there are multiple ways to easily do what I want without any "new feature".

    • remember to only check versioned buckets
    • remember that some applications manage own non-current versions

    StorageGRID ILM for non-current versions does work (see the post at the top), but there's no reason to let misbehaving apps pile up a ton of useless versions just because a bucket has versioning enabled.

    A self-service clean-up CLI tool can be provided to users to prune excessive old versions of objects they no longer need.

    For repeat offenders, daily prune jobs can be scheduled from popular job schedulers. There's no need to micro-manage these things with StorageGRID ILM: yes, you should have a broad clean-up policy, but not create rules for every misbehaving application.

    And finally, S3 applications should be able to prune own aged versions in any case. If they don't, create a feature request for your S3 application vendor or community project.
