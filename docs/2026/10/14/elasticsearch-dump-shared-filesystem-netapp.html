    Dump Elasticsearch 9.5 snapshots to shared NetApp filesystem

    2026-10-14 00:00 5 minute read

    On this page

    • Introduction
    • Workflow
    • Conclusion
    • Appendix A: API response (snapshot)

    Introduction

    In my opinion, S3 is the only valid choice for Elasticsearch snapshot destination.

    Some users of on-premises Elasticsearch prefer to use a shared filesystem. Maybe they think the cost is lower (it's likely not), or don't want to have on-premises S3 (that's fine, but there's no other place big data should go and by delaying they just increase technical debt in their infrastructure).

    Do you think Elasticsearch serverless (in Elastic Cloud) or AWS OpenSearch serverless use shared POSIX storage? Or could they be doing something that Splunk SmartStore does on-premises and in the cloud?

    In 2023, I blogged about taking Elasticsearch 8snapshots to StorageGRID. This post is for the POSIX hold-outs: Elasticsearch 9 supports taking snapshots to a shared POSIX filesystem, so here's how I'd do it if I had to use a shared POSIX filesystem.

    Workflow

    • Configure shared filesystem in all Elasticsearch instances in the cluster and do a rolling restart
    • Verify compatibility - this is so that you don't use an unsupported configuration
    • Snapshot and check

    Add a path on BeeGFS to Docker Compose mounts (or edit Elasticsearch configuration YAML for VMbare metal) on all nodes, and perform a rolling restart of Elasticsearch.

    To configure:

    Check the containers to make sure the shared BeeGFS filesystem is mounted and accessible:

    Notice that, in the screenshot above, Elasticsearch Docker Compose is also on BeeGFS. But the images and main volumes are in the usual Docker store. Only the shared filesystem path (for snapshots) is on BeeGFS (BeeOND). You shouldn't have Hot tier on BeeGFS.

    BeeOND is used because it's easier to set up (I have a nice little script that takes 30 seconds to stand it up), but normally you'd use the non-BeeOND BeeGFS. Functionally, they're the same.

    Verify shared filesystem:

    Configure step with _snapshot/<target>:

    PUT _snapshot/beegfs
{
  "type": "fs",
  "settings": {
    "location": "/mount/backups/beegfs"
  }
}

    Response:

    {
  "acknowledged": true
}

    Verify step with /_snapshot/<target>/_verify:

    POST /_snapshot/beegfs/_verify

    Response:

    {
  "nodes": {
    "Tvo0Dzj8RjWK3ixFHpyTWA": {
      "name": "71f8e2b8a6b0"
    }
  }
}

    Upload some data.

    I uploaded 300K records from SGAC, my "StorageGRID audit log to JSON (or Parquet)" converter.

    The SGAC input collection wasn't large (170MB JSONL), but it was more than just a blip.

    The snapshot was taken with wait_for_completion=true, global state was included to make more data get dumped to disk, and ignore_unavailable was set to false to report any errors.

    POST /_snapshot/beegfs/01-sean-snap?wait_for_completion=true 
{
    "ignore_unavailable": false,
    "include_global_state": true,
    "indices": "sgac",
    "metadata": {
        "taken_by": "scaleoutSean",
        "taken_because": "LFG"
    }
}

    Like with Ray checkpointing, I/O lagged due to OS write buffering, but seconds later it appeared in disk I/O measurements and was nicely distributed across all constituent volumes.

    Elasticsearch snapshot dump to disk worked. Over 400 MB was dumped to BeeGFS. Response from that call is lengthy so I put it in Appendix A at the bottom (of the second snapshot, because I forgot to preserve output of the first).

    Conclusion

    NetApp doesn't have this BeeGFS solution featured, but the fact that it passes Elasticsearch 9 validation makes it supported by Elasticsearch and ThinkParq.

    With BeeGFS, we can dump Elasticsearch to disk at whatever speed we get from the storage. With E-Series E4000, that can be 5-10 GB/s to NL-SAS and a lot more with hybrid EF-Series EF50 and EF80 (which have NVMe controller shelf, but can attach NL-SAS expansion shelves).

    In fact, with hybrid EF-Series used for snapshots there's little reason to use other storage for Elasticsearch because you can solve Hot Tier in the same array(s). You can move Elasticsearch to Kubernetes (or keep it on bare metal or in VMs), you can dump snapshots to a shared filesystem on NL-SAS, and you can get best NVMe performance possible from a NetApp disk array (see about the EF80 here).

    BeeGFS can run out of VMs and for large Elasticsearch clusters you could put BeeGFS into own cluster and run Elasticsearch in Kubernetes (use BeeGFS CSI to mount shared filesystem). If you have dozens of Elasticsearch nodes and need to dump data at tens of GB/s…

    BeeGFS 8 has RST, a feature that syncs BeeGFS files to/from S3. RST lets you ship ("push") BeeGFS contents to S3 (e.g. some public cloud with ILM set up to move it to a low cost tier). Even if BeeGFS gets destroyed, snapshot data can be recovered from another BeeGFS cluster, or even accessed directly from authorized S3 clients.

    With this approach, while your snapshot dumps still use a shared POSIX filesystem, at least everything is modern. If you decide to tap out and get with the program (S3), the same E-Series storage arrays can be consumed from StorageGRID SDS VMs without investment in new hardware (you'd get a performance penalty because of increased redundancies in S3, but mostly eliminate the need to make a copy in public cloud).
